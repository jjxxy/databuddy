# v0.19 Agent 协作：产品判断与上线边界

核对日期：2026-10-23。本文依据当前代码和下列官方规范。实际执行记录以发布包的 `VALIDATION-v0.19.0.json` 和 `verification/v0.19.0/` 为准；没有记录的测试不能视为通过。

## 先纠正目标中的前提

“史上最强”和“所有能力完美”都没有可验证的比较标准。多个Agent也不会自然提高准确率：相同模型、相同上下文中的多个角色可能重复同一个错误；投票不能代替完整取数、确定性计算、控制数与来源核对。正式使用应约定业务正例、异常负例、完整交付、可恢复性、权限和费用等验收指标。

本产品继续聚焦财经业务用户的持续工作空间。协作应让主Agent分派必要的专业检查，集中给用户交付成果；不应把多个聊天窗口和大量内部消息变成业务用户的新工作负担。

界面同样需要克制：顶部与侧栏围绕项目、会话、资料和成果组织；连接、模型供给及企业接入由管理员配置。项目和会话删除采用可恢复的软删除，并明确恢复入口。删除记录不能宣传为撤回已发送的数据或第三方已经发生的动作。

成果应能在页面中直接检查并继续修改。数值表须保持精确格式、提供完整分页和行数，不能用预览代替全量。DOCX/PPTX的文字或结构预览与实际分页、排版和渲染是不同证据，须清楚标注；预览中的HTML、链接和文件内容按不可信输入安全渲染。界面是否真正简单、删除恢复和预览是否可用，需真实浏览器验收，不能仅由静态代码或接口测试推定。

## 本轮协作的三种边界

| 路径 | 合理用途 | 不能据此推导 |
| --- | --- | --- |
| 内置只读专业Agent | 并行核对数据结构、财经口径和报告证据；使用真实模型会话及已有受控读取工具 | 角色名称等于资质认证；子Agent结论等于正式指标审批 |
| 调用外部Agent | 将明确选择的资料或完整结果交给已配置、已授权的服务处理，跟踪真实任务和交付件 | 任意第三方Agent都可信、都兼容同一协议、都会遵守它自报的只读承诺 |
| 被其他Agent调用 | 以独立、可撤销、有期限的服务凭据提交限定项目的任务和获取本任务成果 | 工作空间口令可以当通用服务凭据；项目级授权等于逐文件隔离 |

协作必须贯穿真实的任务状态、来源版本、模型版本、数据范围、费用预算、交付清单和取消路径。主Agent不能在子任务仍等待、失败或提交结果未知时，用一句“已完成”覆盖这些事实。

## 官方协议核实与版本选择

截至本次查阅，A2A官方“latest”页标明最新发布为 **1.0.0**，并列出0.3.0为旧版本。1.0存在实际线格式变化：接口通过`supportedInterfaces`声明；JSON-RPC方法为`SendMessage`、`GetTask`、`CancelTask`；消息角色和任务状态使用枚举名；Part不再带旧版`kind`。因此，能接收0.3消息不能宣传为已经支持1.0。

1.0另有容易忽略的语义：`configuration.returnImmediately`未设或为false时默认等待任务终止/中断。提供异步子集时，应明确使用true，或对不支持的等待方式返回错误，不能无说明地返回进行中任务冒充完整规范实现。流式推送、通知、gRPC、动态授权与某一非流式HTTP配置能够工作，是不同的兼容层次。

MCP标准提供工具发现、参数结构和调用结果，并非“工具被另一Agent调用就自动变得安全”。工具注解不是授权证据；服务端和客户端都应限制真实可调用的工具与数据范围。MCP官方安全文档还明确反对令牌透传，要求防范混淆代理、SSRF、会话劫持和权限过宽。

| 官方来源 | 本次核实内容 |
| --- | --- |
| [A2A latest specification](https://a2a-protocol.org/latest/specification/) | 1.0.0版本、版本协商、接口/Part/角色/状态、异步与默认阻塞语义、协议安全要求 |
| [A2A 0.3.0 specification](https://a2a-protocol.org/v0.3.0/specification/) | 旧版JSON-RPC和Agent Card；完成、失败、取消、输入要求和认证要求的区别 |
| [MCP 2025-11-25 Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) | 工具发现/参数、可见操作和人工控制的交互原则 |
| [MCP Security Best Practices](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices) | 禁止令牌透传、防SSRF、会话安全、最小权限 |

本版确切支持的传输、版本、方法和限制见 `AGENT-GATEWAY.md`、`AGENT-COLLABORATION.md`。没有进行商业竞品实机准确率或性能对标，不能从公开功能列表推导同等能力。

## 需要独立验收的关键问题

- **身份和权限**：服务凭据只能使用授权项目和任务，不能访问普通业务/后台接口；撤销和过期必须对正在运行的任务生效。服务身份不继承人的个人记忆、私有MCP或个人Skill。当前项目基础权限仍需结合既有共同拥有的工作空间范围理解。
- **重复与未知结果**：提交到远程后超时，不能简单当成“没有提交”。应保存提交阶段与幂等编号，结果不确定时标记unknown并核对，不能自动重投产生重复任务或外部副作用。
- **状态与业务验收**：HTTP成功、A2A终态、聊天state=done和财经结果验收通过不是同一件事。需要补充信息、部分完成、阻断和失败必须原样传达。
- **完整数据**：交接的是固定版本、带摘要的完整资料/结果；预览不能冒充全量。超过交接预算应明确阻断或选择可验证的分页/大文件机制，不能截断后标记complete。
- **费用与延迟**：子Agent模型请求、上下文和输出应计入整体预算。并发会缩短部分等待，但可能增加总调用量；汇总、修正、压缩和失败重试也有成本。上游未返回用量时，不能把费用显示为零。
- **循环与放大**：限制嵌套深度、扇出、并发、任务数量和截止时间，避免A调用B、B再调用A无限扩散。允许反方向发起新的独立授权任务，不等于允许同一条任务链无限回调。
- **结果可信度**：字节摘要只能证明传输和保存一致，不能证明远程计算的业务含义正确。接收结果需保留来源、单位、期间、粒度和语义核阅状态；远程文字和清单也是不可信输入。
- **恢复和取消**：进程重启后恢复状态和已完成步骤；取消应区分已请求、对方确认取消和结果未知。不能保证撤回已经发出的数据，或回滚第三方已经发生的副作用。

## 企业使用还需要什么

本轮协作能力不是完整企业生产资格证明。现有默认部署仍是单实例、共同拥有的工作空间；个人资源隔离不等于互不信任租户之间的项目、存储、队列和连接数据隔离。OpenCode多副本原生会话恢复、跨节点故障切换、SLO与容量、SSO/审计留存、备份灾备、模型和第三方数据合规，均需实际部署验收。

本地模式和仅本地连接也不等于每个进程都有操作系统隔离。可信stdio程序及应用进程的文件权限、网络访问、外部代理转发等边界仍遵循v18复核，不会因为加入Agent协作而自动变成沙箱。

上线时至少分开记录：代码回归、真实协议互通、真实模型财经任务、目标OS/Docker部署、身份系统、故障恢复、负载和严格离线。某一层通过不能替代另一层；未执行项目标记“未验证”，不要用总通过率掩盖关键缺口。

## 本轮集成中发现并修正的问题

真实双实例测试发现：机器任务安全分支曾越过异步数据工作流恢复，导致已排队的工具缺少真实完成回执；该分支现先恢复后台任务再规划下一步。OpenCode原生会话还曾对压缩请求沿用普通请求的8万字符门槛，使需要缩小的历史无法进入压缩。运行时现仅为受信任插件明确识别的压缩请求提供更高、有限的单次上限；普通请求仍受8万字符门槛约束，压缩仍计入原任务、服务客户端和父子Agent共同预算。

原生工具回执现在只附加新增或变化的工具定义，避免每一步重复发送完整Schema；原工具记录和原文仍可回查。管理员可通过`ATLAS_OPENCODE_MODEL_INPUT_CHAR_LIMITS`设置按模型ID的保守输入字符限制（JSON对象，例如`{"finance-model":120000,"*":80000}`），通过`ATLAS_OPENCODE_COMPACTION_MAX_INPUT_CHARACTERS`限制压缩请求（默认240000，绝对上限320000）。字符限制不是任意供应商的精确Token计数；部署者仍需按实际模型上下文窗口和输出预留设定限制并实测，未知上游用量不按零费用处理。

当前集成证据实际启动两个Atlas API/Agent/Worker进程组与OpenCode 2.1.2，模型使用明确的本机确定性HTTP夹具。跑通A→B的A2A 1.0与B→A的独立授权MCP任务、40行完整原件/结果和`300.000000000002`精确控制数、两个不同原生会话的并发只读专业Agent、共同持久预算、幂等冲突、运行中取消、撤权、未知提交不重发及重启后状态/已完成回执保留。记录有7次实际原生压缩；优化后实际请求低于普通单次上限，更高压缩限额的边界由针对性单测覆盖。

这些证据证明真实进程和协议执行链路，不能证明商业模型能够独立理解任意财务表格。夹具预定义工具选择，实际文件写入、队列加工、哈希核对和状态恢复由应用执行。真实LLM月报准确率、完整财务验收、Docker/目标OS、HA、负载和严格离线仍分别验收。

具体业务验收见[新增协作验收](../acceptance/finance_monthly/V19-AGENT-ACCEPTANCE.md)，既有财经标准答案继续使用原月报验收包；答案不提供给模型。


## 导航与成果的产品依据

参考[ChatGPT Projects 官方说明](https://help.openai.com/en/articles/10169521-projects-in-chatgpt)将持续工作的对话、资料与规则收拢到项目；参考[Claude Artifacts 官方说明](https://support.claude.com/en/articles/17153992-what-are-artifacts-and-how-do-i-use-them)把可复用成果放在对话旁边，方便查看并继续修改。这是交互结构的借鉴，不是竞品排名或同等能力声明。

本版左侧只保留项目与所属对话，行内菜单提供重命名和移到回收站；协作、能力与记忆、动态、业务任务、应用、历史和回收站收进工作设置。顶部保留项目位置、管理员供给模型的选择和成果入口。右侧成果目录按类型和版本查看真实文件、完整表格分页、报告正文、图表和Office内容；继续修改会带入成果引用生成草稿，由用户提交。

需要明确的差距：当前没有Word/PPT原版式在线编辑器，也没有保证任意HTML/网页程序能安全运行的通用画布。DOCX/PPTX展示提取的段落与表格；PDF提供原件下载；不支持的格式给出清楚提示。正式交付前仍需在目标Office软件中核对排版及公式重算。目录按通用存储记录扫描，历史量很大时需要资产索引和容量测试。
